# Architecture

The phase-1 legacy system for the modernization experiment in `PROJECT_DESC_HUN.md`. Its job is to
be a realistic, *running* heterogeneous enterprise landscape that MCP servers, agents and Google UCP
can later be layered on top of. Those later phases are not in this repository.

## The shape of it

Three services own three databases and share nothing. There is no shared library between them, no
shared schema, and no joins across them. Every cross-subsystem fact has to travel over a wire and
be translated on arrival.

## The four API styles

The heterogeneity minimum in `INITIAL_DESIGN.md` asks for at least three kinds of API. There are
four.

| Style | Where | Notes |
| --- | --- | --- |
| **REST/JSON** | `catalog-service`, `activation-service`, billing's Stripe webhook | Errors as `{code, message}` + HTTP status |
| **SOAP 1.1, contract-first** | `billing-service` at `/ws`, WSDL at `/ws/billing.wsdl` | XSD is the contract; JAXB stubs generated by `xjc`; errors as SOAP faults |
| **Batch fixed-width file exchange** | `billing-service` outbox/inbox | No envelope, no schema, no field names — only column offsets agreed out of band |
| **Direct JDBC against another subsystem's schema** | `ops-console` reading `catalog` | The classic legacy shortcut: no API at all, just SQL against someone else's tables |

Plus one asynchronous interaction model that is not a protocol: Flowable message correlation with a
non-interrupting boundary timer.

Protocol variety alone would not satisfy the brief. The data models differ *semantically* as well —
that inventory is in [`semantic-mismatches.md`](semantic-mismatches.md), and it is the more
important document.

## Subsystem 1 — catalog and subscription registry

Port 8081. Database `catalogdb`, schema `catalog`.

The product catalogue and the subscription register: what can be bought, who bought it, and what
state each subscription is in.

* **Tables** `plan`, `subscriber`, `subscription`.
* **Persistence** hand-written SQL through `JdbcTemplate`. No ORM, deliberately — the ops console
  reads these same tables directly over JDBC, so the schema *is* part of the public surface.
* **Legacy shape** zero-padded `CHAR(8)` customer numbers; two-character status codes
  (`NW PA AC SU TE`); a one-character service kind (`I`/`M`); `Y`/`N` flags; data allowances in
  megabytes with `-1` for unmetered; money as an integer count of HUF fillér.
* **Real behaviour worth knowing about**
  * Activation is idempotent: activating an already-active subscription is a no-op, because
    Flowable retries jobs.
  * Add-ons are their own subscription rows hanging off a base one, and they only grow the parent's
    effective allowance once *they* become active.
  * A plan change recomputes the effective allowance from the new base plus every surviving add-on.
  * An unmetered base plan stays unmetered no matter what is bolted onto it.
  * Withdrawn plans (`active_flag = 'N'`) stay in the table for historical subscriptions but are
    hidden from the catalogue and refused for new orders.

## Subsystem 2 — activation process

Port 8082. Database `flowabledb`: Flowable's engine tables in `public`, activation's own
`activation_order` table in schema `activation`.

**Flowable 7 is embedded as a library.** There is no separate Flowable deployment, no Flowable REST
app and no Flowable UI — the engine is a jar inside this Spring Boot service, as
`PROJECT_DESC_HUN.md` requires.

* **One BPMN process, three variants.** `subscriptionActivation` covers a new subscription, a plan
  change and an add-on purchase; an exclusive gateway on `changeType` is the only place they differ.
* **Asynchronous.** `validateOrder` and `issueInvoice` are `flowable:async`, so `POST /orders`
  returns `202 Accepted` with the order in `RECEIVED` and nothing done yet. A client cannot learn
  the outcome from the response that started it — which is why status polling is a service in its
  own right rather than a convenience.
* **Message correlation.** After requesting provisioning the process parks inside a
  `waitForProvisioning` sub-process on a `provisioningCompleted` message catch event, correlated by
  the process instance's business key (the order number). The simulated network platform calls back
  over HTTP, from another thread, after a delay.
* **A non-interrupting boundary timer.** `cancelActivity="false"` is the single most important
  attribute in the BPMN file. When the provisioning SLA is blown the timer fires, a delegate reports
  the order as `STUCK`, and **the wait stays in place**. That is what makes failure branch A
  repairable: ops can correlate the missing message later and the process finishes normally instead
  of having to be restarted.
* **Its own dialect.** `ORD/2026/0000001`; `customerRef` as a plain integer; `offerId` as dotted
  lowercase; gigabytes as a decimal; HUF major units; `CHAR(8)` `yyyyMMdd` dates; E.164 phone
  numbers *with* the plus; spelled-out statuses.
* **Its own clients.** `CatalogRestClient` and `BillingSoapClient` are hand-rolled here and are
  **not** shared with `subsystem-clients`. See `decision-log.md` DL-009.

### The process

```
orderReceived
  └─> validateOrder                     [async]  catalog REST; rejects with a BpmnError, not a retry
        └─> changeTypeGateway
              ├─ NEW_SUBSCRIPTION -> reserveSubscription   catalog REST, creates the row in PA
              ├─ ADDON            -> reserveAddon          catalog REST, child row in PA
              └─ PLAN_CHANGE      -> applyPlanChange       catalog REST, already-active row
                    └─> changeTypeJoin
                          └─> requestProvisioning          fire and forget to the network platform
                                └─> [waitForProvisioning]  parks on message provisioningCompleted
                                      ⋮
                                      ├── boundary timer (non-interrupting, ${provisioningTimeout})
                                      │     └─> markStuck ──> stuckReported     (side branch ends)
                                      ⋮
                                      └── message arrives (platform, or ops by hand)
                                            └─> completeActivation   catalog REST (skipped for PLAN_CHANGE)
                                                  └─> issueInvoice   [async]  billing SOAP
                                                        └─> markProvisioned ──> orderCompleted
```

## Subsystem 3 — billing and payment

Port 8083. Database `billingdb`, schema `billing`.

Three protocols in one subsystem, which is the point of it.

* **SOAP** for the enterprise. Contract-first from `xsd/billing-v1.xsd`; WSDL generated and served at
  `/ws/billing.wsdl`. Seven operations: `getInvoices`, `createInvoice`, `startPayment`, and the four
  ops-only ones (`exportPaymentBatch`, `listUnconfirmedBatches`, `getPaymentBatch`,
  `reconcileBatch`).
* **Batch fixed-width files** for the clearing house. Outbound `PMT-<batchId>.txt` records are
  HDR 61 / DTL 85 / TRL 24 bytes; inbound `ACK-<batchId>.txt` are ACK 57 / RES 35. Money is an
  implied-two-decimals integer. A background poller sweeps the inbox, so the settlement leg is
  genuinely asynchronous — nothing in the request that paid the invoice is still waiting for it.
* **Stripe REST**, outbound through the official Stripe Java SDK, and one inbound REST webhook for
  `payment_intent.succeeded`.

* **Tables** `billing_account`, `invoice`, `payment_batch`.
* **Its own dialect.** `BA-00042`; `customer_ref` as a plain integer; `2026/INV/000001`;
  `NUMERIC(12,2)` major units with a **net-led** breakdown and 27% VAT computed here; `yyyy-MM-dd`
  date strings on the wire; SOAP faults instead of HTTP statuses.
* **The payment lifecycle is three-legged on purpose.**
  `OPEN` → (Stripe confirms) → `SETTLEMENT_PENDING` → (clearing house acknowledges) → `PAID`.
  The middle state is money Stripe has taken that this business does not consider posted. That gap
  is where failure branch B lives.

## Mocked versus real

`PROJECT_DESC_HUN.md` asks for a working system, not a mock one. Two things are mocked, because the
alternative teaches nothing:

| Mocked | Why, and how honestly |
| --- | --- |
| **Stripe** | No real account exists. `stripe/stripe-mock` (the official image) under compose, `stripe-sim` on the local path, both spoken to through the real Stripe Java SDK over HTTP. Swapping in a real `sk_test_` key is two properties. |
| **The network provisioning platform** | Real SIM and line provisioning means an OSS that owns physical inventory. The simulator lives inside `activation-service` but calls back **over HTTP to the public callback endpoint**, from a scheduled thread — nothing short-circuits into the engine. |
| **The clearing house** | Inside `billing-service`, reading and writing the same real files on the same real filesystem an SFTP partner would. Its `/sim/clearing-house/config` endpoint is the fault injection point for failure branch B. |

Everything else — the databases, the migrations, the SOAP stack, the WSDL, the file formats, the
process engine, the job executor, the timers, the HTTP calls between services — is real.

## The internal subsystem-client layer, and where phase 2 plugs in

`subsystem-clients` is a library, not a service. It holds:

* a **canonical model** (`Money`, `DataVolume`, `CanonicalPlan`, `CanonicalSubscription`, …) that
  belongs to none of the three subsystems;
* **`SemanticMappers`**, one place where every legacy dialect is translated to and from it;
* four clients, one per protocol: `CatalogJdbcClient` (direct SQL), `CatalogRestClient`,
  `ActivationRestClient`, `BillingSoapClient`, `BatchFileClient`.

`ops-console` is its only consumer today. In phase 2 the MCP servers and the UCP adapter sit on
exactly this layer, which is why it exists now rather than being invented later. See
[`phase2-seams.md`](phase2-seams.md).

## The two failure branches

Both are, at bottom, the same thing: **a state that exists in one subsystem and cannot be expressed
in its neighbour.**

### A. Stuck activation
The network platform never calls back. The boundary timer fires, the order goes `STUCK`, and the
catalog is left with a subscription in `PA` that is indistinguishable from one about to succeed. The
catalog has no word for "stuck"; activation has no visibility of the catalog's row.

*Trigger* `simulateStuck: true` on the order, or the global off switch at
`POST /activation/v1/ops/provisioning-platform`. A stale `PA` row is also seeded
(`SUB-2026-000009`) so the inconsistency is findable from a cold start.
*Detect* `GET /ops/v1/diagnostics/stuck-activations` — correlates activation's waiting instances
(REST) with the catalog's stale `PA` rows (**direct JDBC**). Neither source alone is enough.
*Resolve* `POST /ops/v1/remediation/activation/{orderNo}/force-provision` injects the missing
correlated message with a hand-supplied ICCID and the process completes normally; or `.../cancel`
gives up and rolls the subscription back.

### B. Unconfirmed billing batch
Stripe took the customer's money, the settlement batch went out, and the acknowledgement never came.
The batch sits in `SENT` and its invoices in `SETTLEMENT_PENDING` — a state neither the catalog nor
activation can represent.

*Trigger* `POST /sim/clearing-house/config {"ackEnabled": false}`. A stranded batch
(`BATCH-20260925-001`) is also seeded.
*Detect* `GET /ops/v1/diagnostics/unconfirmed-batches`, over SOAP, plus reading the outbox files.
*Resolve* `POST /ops/v1/remediation/billing/batches/{batchId}/reconcile` in one of two modes:
`RESEND` hands the file over again and waits for a real acknowledgement; `RE_DRIVE_ACK` rebuilds the
acknowledgement from the file that was actually sent, for when the money demonstrably moved and the
confirmation is never coming. Both are safe to repeat.

## Scope

`INITIAL_DESIGN.md` sets a ceiling of three subsystems, about four tables, one happy path and one
deliberate failure branch. What was built:

* **3 subsystems** — as specified.
* **7 tables** — 4 core (`plan`, `subscriber`, `subscription`, `invoice`) plus 3 supporting
  (`billing_account`, `payment_batch`, `activation_order`). Flowable's engine tables are not
  counted. The overshoot is argued in `decision-log.md` DL-006; in short, each of the three is the
  vehicle for a required property, and none adds a new domain concept.
* **1 happy path** — start/activate a subscription, with plan change and add-on as `changeType`
  variants of the *same* process definition rather than separate paths.
* **2 faces of the deliberate failure branch** — stuck activation and unconfirmed billing batch.
  `INITIAL_DESIGN.md` names both by name ("elakadt aktiválás **vagy** számlázási
  batch-visszaigazolás"), and they demonstrate the same class of problem in two different
  subsystems, which is what makes the ops story worth telling.
