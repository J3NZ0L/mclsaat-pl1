## 1. What this repository is

The **phase-1 legacy system** for the modernization experiment described in `PROJECT_DESC_HUN.md`: a
deliberately heterogeneous ISP/telco B2C subscription landscape that runs for real. MCP servers,
agents, Google UCP and the tokenomics measurement are **later phases and are not in this repository**.

The point of the system is its *heterogeneity* — different protocols, different interaction models,
and above all **semantically different data models**. `PROJECT_DESC_HUN.md` is explicit that this,
not old code style or technical debt, is the critical legacy property being modelled.

## 3. Things that look like bugs and are the subject matter

**Do not "fix" these.** Each one is deliberate, documented and pinned by a test; silently removing any
of them destroys what the project is measuring. If you have a reason to change one, change the test
and the documentation in the same commit, and record it in the decision log.

1. **The VAT round-trip loses a fillér** (DL-014). The catalog quotes gross consumer prices, billing
   invoices on net and adds VAT back, and both round to two decimals. Of the nine seeded plans,
   `MOB-VOICE-0010` gains one fillér (5990.00 → 5990.01) and `INET-FIB-1000` loses one
   (17990.00 → 17989.99). Pinned by
   `VatCalculatorTest.theRoundTripErrorAcrossTheWholeSeededCatalogIsExactlyThis`.
   *Nobody in the system owns that discrepancy. Deciding who should is a phase-2 question.*

2. **`activation-service` duplicates `subsystem-clients`' translation logic** (DL-009). Both implement
   the catalog's dialect, separately, with their own tests. That is the "before" picture: an MCP server
   replaces N ad-hoc translations with one. Factoring it out now would delete the evidence.

3. **Three names for one customer** — `"00000042"` (catalog), `42` (activation), `"BA-00042"`
   (billing) — with no shared key anywhere. `SemanticMappers.guessBillingAccountNo` is named
   "guess" for a reason: in billing the mapping is a table row, not a format.

4. **`ops-console` reaches into the catalog's schema over direct JDBC.** No API, just SQL against
   another subsystem's tables. This is one of the four required interface styles.

5. **`stripe-sim` exists alongside `stripe/stripe-mock`** (DL-011). Not redundancy: the official mock
   is stateless, and the local path needs a `confirm` that actually changes a status.

6. **Order numbers are query parameters, not path variables.** They contain slashes
   (`ORD/2026/0000001`), Tomcat rejects an encoded `%2F`, and decoding it splits the order number into
   three path segments. The identifier format dictates the API shape.

7. **Timers and thresholds are seconds, not hours.** `PROVISIONING_TIMEOUT=PT20S`,
   `BATCH_UNCONFIRMED_AFTER_MINUTES=2` (DL-017). A production SLA would be hours; a demo cannot wait.

## 4. How to build, test and run

```bash
mvn verify                      # THE test command. Not `mvn test`.
docker compose up --build       # everything, one command
scripts/run-local.sh            # the same thing without Docker
scripts/demo.sh                 # happy path + both failure branches, end to end
```

**`mvn test` is nearly meaningless here.** It runs only the fast unit tests (mappers, VAT arithmetic,
fixed-width record offsets). Everything that matters — real PostgreSQL, real SOAP over a real port, a
live Flowable job executor, real files — is in `*IT` classes that Failsafe runs during `verify`
(DL-003).

### Verifying your work

Whoever writes the code does not get to certify it. **Run it**, do not only look at a green test run:

1. `mvn verify` — all of it, not one module.
2. Start the system (`docker compose up --build` or `scripts/run-local.sh`).
3. `scripts/demo.sh` — it exercises the happy path and both failure branches and exits non-zero if
   any check fails.
4. For anything touching a protocol boundary, poke it by hand too: a raw `curl` SOAP POST, a `psql`
   query against the catalog schema, a `cat` of the settlement file.

## 5. Environment notes (a cloud container)

* **The Docker daemon is not running at container start.** `nohup dockerd > /tmp/dockerd.log 2>&1 &`
  and wait ~8s. It has also been seen to die during a heavy build; restart it the same way.
* **Outbound HTTPS goes through a TLS-terminating proxy on `127.0.0.1`.** Three consequences:
  * `curl` to localhost services needs `--noproxy '*'`, or the proxy swallows it.
  * A bridge-network container cannot reach the proxy, so `docker-compose.yml` builds with
    `network: host`.
  * The JVM inside the build container must trust the proxy's CA:
    `cp /root/.ccr/ca-bundle.crt docker/ca/` before `docker compose up --build`. See
    `docker/ca/README.md`.
  * `apt-get` inside a build fails outright ("the repository is not signed"), which is why the runtime
    image installs nothing and compose health-checks with bash's `/dev/tcp`.
* **Docker Hub rate-limits (HTTP 429).** If a build fails on `load metadata`, pull the base image on
  its own with a retry loop, then build again.
* **`pkill -f <pattern>` can kill the calling shell** (the pattern usually appears in the script text;
  it surfaces as exit 144). Match on `comm == "java"` with `ps` + `awk` instead.
* `repo1.maven.org` rate-limits raw `curl` metadata queries. Let Maven resolve.

## 6. Build traps already solved — do not undo these

| Trap | Fix, in the parent POM unless noted |
| --- | --- |
| Failsafe gets the fat jar on its test classpath and fails discovery with `NoClassDefFoundError` | `spring-boot-maven-plugin` uses `<classifier>app</classifier>`, so the runnable jar is `target/<module>-1.0.0-SNAPSHOT-app.jar` (DL-004) |
| Integration tests cannot find Docker: `client version 1.32 is too old` | Failsafe passes `-Dapi.version=${docker.api.version}`, default `1.44` (DL-005) |
| `ExecutionQuery.processInstanceBusinessKey(...)` silently reports nothing waiting | The business key is on the process instance's own execution row; the message subscription is on a child execution. Resolve the instance first, then query by `processInstanceId` (DL-016) |
| A rejected order stays in `RECEIVED` with no reason | An unhandled `BpmnError` from an async service task rolls the transaction back, taking the status write with it. The reject path has an error boundary event and a separate `markRejected` delegate |
| A `PT5S` timer fires at t+13s | Flowable polls for due timer jobs every 10s by default; `flowable.process.async.executor.default-timer-job-acquire-wait-time: PT1S` |
| `stripe-mock` rejects the API key with `AuthenticationException` | The key must be alphanumeric after `sk_test_`. `sk_test_mclsaat123` works, `sk_test_mclsaat_local` does not |
| Activation ITs hang waiting for a callback | The simulated platform calls back over real HTTP, so the tests use `DEFINED_PORT` (18082), not `RANDOM_PORT` (DL-015) |
| Flowable ITs fail on mock verifications at random | The shared job executor runs leftover instances from earlier tests. `SubscriptionActivationProcessIT` drains them in `@BeforeEach`, retrying on optimistic-locking collisions |

## 7. Conventions

* **Java 21, Spring Boot 3.5.6, Flowable 7.2.0, PostgreSQL 16, Maven.** Versions are pinned in the
  parent POM; change them there, never per module.
* **Each subsystem keeps its own dialect.** Do not normalise identifiers, units or status vocabularies
  at a subsystem's boundary to make a caller's life easier — the whole point is that the caller has to
  translate. Translation belongs in `ActivationSemantics` (inside activation) or `SemanticMappers`
  (inside `subsystem-clients`).
* **Hand-written SQL through `JdbcTemplate`, no ORM.** The schemas are part of the public surface.
* **Idempotency is not optional.** Flowable's async executor retries and Stripe re-delivers webhooks,
  so every operation either carries an idempotency key (`requestRef`, the order number) or is
  idempotent by inspection.
* **Unknown enum values become `UNKNOWN`, never the nearest guess.** A plausible wrong status is worse
  than an obviously unhandled one.
* **Comments explain *why*, not *what*.** The existing code assumes a reader who can read Java and
  cannot read minds — match that. Do not add comments that restate the line below them.
* **Tests are named as sentences** (`aWithdrawnOfferIsRejectedBeforeAnythingIsReserved`) and assert on
  behaviour a reader would care about, not on implementation detail.
